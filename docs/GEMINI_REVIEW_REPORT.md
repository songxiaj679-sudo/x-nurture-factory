### 小規模アカウントの成長と宣伝計測（本番未反映）

- JITはURL・指示が一致する保存済み戦略と本人の実績を優先し、公式取得かつ連携先一致のフォロワー数がある場合、少し上の規模の外部投稿構造を補助的に参照します。単時点の比較は成長履歴を証明せず、元投稿文は渡しません。実績に照らし次の切り口を検討するモデルへの指示であり、保存済み戦略レポートは自動更新されません。
- 初期・段階未確認では宣伝枠を作らず、既存JIT枠も情報提供として扱います。URLらしい文字列を含む自動投稿と宣伝指定の既存非JIT投稿は停止します。公式自律エンゲージメントのAI返信・自動フォローはX承認未取得のため全段階で停止します。検出は完全ではなく、他経路や明示的な手動投稿は対象外です。段階確認済みの他アカウントではプラン別の宣伝枠を使います。
- 信用構築の目標はフォロワー100人または1投稿の24時間ビュー1,000回。100人未満または初期と診断された連携アカウントは信用構築に固定し、目標達成でも自動移行しません。厳密な24時間値の測定と手動フェーズ変更画面は未実装です。返信・フォロー候補の確認後実行と日別上限（100件・10件）も未実装です。
- ASP日別クリック・成約を手入力しユーザーと宣伝先別に保存、最新7記録をJITに渡します。他媒体を含み得るため、個別投稿の成果とは扱いません。宣伝先変更時の保存は拒否し再読込を求めます。ASP規約・法令の確認、成約の自動計測は未対応です。
- モックとFirestore Emulatorで投稿の段階別制御、PR付き英語投稿、ユーザー・URL分離、不正値、戦略変更時の停止、画面の日英表示を検証しました。実Gemini・実X API・本番DBの検証、本番反映や実投稿は行っていません。

### JITの宣伝先・実績参照と一時障害への対応（本番未反映）

- 新しいX API収集分には収集経路と指標の有無を記録します。数値の投稿ID以外のシード等はJIT集計から除外しますが、数値IDだけで実在や正確性を証明できません。ローカルの474件中、今回の集計は32グループ・358件・19ジャンルを代表しましたが、すべて出所未検証の旧記録です。本番環境の件数・品質は未確認です。
- JITは取得ページから業種と読者を推定し、異業種・他言語の構造を転用するようGeminiに指示します。これはモデルへの指示であり、分類結果の検証や、業種別の成果改善は保証されません。
- 既存バッチは4時間ごとに動く設定ですが、特定の2ユーザーの認証情報を使った検索が中心で、登録された約100アカウントがそれぞれ収集していることを確認できません。実環境のバッチ稼働・X API接続・収集結果は未検証です。JITでの顧客間実績共有は今回実装しておらず、他顧客の個別履歴を読んでいません。顧客情報の共有には同意・アクセス制御・匿名化等の設計が必要です。
- サイトの一部の一時的な取得エラーは最大3回試行します。Geminiはタイムアウト30秒、認識できる一時障害時に最大3回試行します。429はSDKが認識可能な30秒以内の再試行待機時間を返す場合のみ再試行します。失敗が続いた場合はジョブを失敗として記録し、後から自動再試行しません。X送信の自動再試行は追加していません。再試行によってGeminiの利用料金が増える可能性があります。
- Firestore Emulatorと外部APIモックで実績のユーザー分離・不正値除外を検証し、モックで内容引き渡し・送信停止・再試行上限・タイムアウト時の中断を検証しました。実Gemini・実X API・本番DBは未検証で、本番反映や実投稿は行っていません。
- **本番投入前の重要課題**: 既存のURL取得はリダイレクト先や内部ネットワークへのアクセスを安全に制限せず、応答サイズも制限しません。JITでの利用が取得機会を増やすため、公開サービスとして使う前に対策が必要です。取得ページ、URL、ユーザー指示はGeminiへ送信されるため、機密情報を含めないでください。外部ページからの指示混入や生成内容の正確性も完全には防げません。
- 長時間の障害後の自動復旧、メール等の能動的な通知、投稿準備中の一時停止の送信直前再確認は未実装です。失敗はジョブ一覧で確認してください。X送信結果が不明な場合はX上で確認し、無条件で再投稿しないでください。

- 計画・執筆・推敲の指示から一部の未確認の断定を除き、未提供の体験や数値を創作しないよう明示しました。AIの出力の正確性までは保証できません。

### 投稿ワーカーの処理能力と巡回時刻（本番未反映）

- 巡回が長引く場合、後続予約の時刻判定が巡回開始時のままになっていた問題を修正しました。各予約を確認する時点の時刻で判定し、取得時にも予定日時を再確認します。
- 1,000顧客が同時に1件ずつ投稿するケースを、実ワーカー・インメモリDB・X APIモックで検証しました。手動指定の固定本文を使いAI生成を行わず、タイマーの巡回関数を直接呼び出しています。1ワーカーは1巡回最大3件のため、全件に334巡回が必要でした。1分周期なら最初の巡回から最後まで少なくとも333分（5時間33分）かかります。実際はAI生成、X API、DB処理、前回巡回との重複抑止によりさらに遅れる可能性があります。
- これは処理上限のシミュレーションであり、本番負荷試験ではありません。日時が巡回中に到来するケースと既存の投稿安全性を含むモックテスト6件、Firestore Emulatorでの予約探索・取得テスト1件が成功しました。実X APIと1,000顧客の同時負荷は未検証です。

### 単発投稿の限定的な照合・復旧（本番未反映）

- X APIの単発投稿成功後に保存だけ失敗し、成功応答の印と投稿IDを失敗記録に保存できた新しいジョブに限り、所有者が画面から照合できます。連携中のXアカウントの直近100件でIDと投稿日時が確認できた場合のみ、再投稿せず履歴を復旧します。復旧時刻、操作ユーザー、確認したXユーザーIDを記録し、照合中にジョブまたはユーザーが変更された場合は復旧を拒否します。
- この照合ではトークンを自動更新せず、応援キャンペーンの再登録も行いません。期限切れやAPI制限・閲覧権限の不足、直近100件に含まれない場合は照合できません。X APIの利用料金が発生する可能性があります。
- Firestore Emulatorと実クライアントのHTTPモックで、OAuth 1.0a・2.0のリクエスト、認証失敗、レート制限、照合中の再連携、競合、復旧後の再送拒否を確認しました。関連モック・画面テスト21件とEmulatorテスト6件が成功しました。実X APIと実ブラウザーは未検証です。
- [X公式のGet Posts仕様](https://docs.x.com/x-api/users/get-posts)では `max_results` は最大100、OAuth 2.0のユーザートークンには `tweet.read` と `users.read` が必要です。公式仕様のホストは `api.x.com`、実装は `api.twitter.com` のため、実環境での接続・認証互換性は未確認です。
- **制約**: 古いジョブ、記録保存前の停止、処理中ジョブ、ID未記録、送信結果不明、スレッドは対象外です。見つからないことは未投稿の証明ではなく、自動再投稿もしません。完全な二重投稿防止や1,000顧客の安定運用は保証できません。

### 合議予約の再送防止と投稿確認情報（本番未反映）

- 承認済みの合議セッションは再度予約できず、HTTP 409を返します。予約を削除した後も同じセッションは再利用できず、別の予約には新しい案が必要です。同じ状態からの同時確定も一方だけが成功します。
- 処理中・失敗したジョブに、保存済み本文と記録された数字の投稿IDへのXリンクを表示します。保存本文は投稿完了の証明ではないと日英で案内します。

- **制約**: この表示は手動確認を支援します。照合・復旧は上記の限定的な単発投稿のみが対象です。IDが記録されていない場合やスレッド途中で結果が不明な場合、照合には別途対応が必要です。他の予約経路間の競合や過去の重複予約も未解決です。

投稿履歴（`GET /api/autopilot/jobs`）の読み取り負荷を改善するため、Firestoreの `orderBy` を活用する「ソート用フィールド」新設について設計を検討しています。方式は未決定であり、実装、移行スクリプトの作成、インデックス配備、本番データ・実X API・PM2の操作は行っていません。

#### 1. ソート用フィールドの形式とID順の扱い
既存の日時フィールド（`postedAt` 等）を直接上書きせず、クエリソート専用のフィールドを設ける案です。形式と仕様変更には課題があります。

- **案A（文字列複合キー）**: `15桁のUnixミリ秒_ドキュメントID`（例: `001732000000000_job1`）。
  - *課題*: 単一フィールドでソートできる利点があるが、負の日時（1970年以前）や桁数の変化に対して文字列ソートが崩れる。また、ID部分の比較がFirestoreのバイト辞書順になる。
- **案B（数値フィールド ＋ ネイティブID順）**: 日時のフォールバック計算結果を `sortTimeMs`（数値）として保存し、`.orderBy('sortTimeMs', 'desc').orderBy('__name__', 'desc')` を検討する。
  - *課題*: 負の日時も数値として扱えますが、日時変換の型・範囲、複合インデックス、同日時の `__name__` 順を検証する必要があります。
- **ID順の仕様変更**: 現行のインメモリソートは `localeCompare` を用いるため、Firestoreの順序と異なり得ます。この差と影響を隔離テストで評価し、仕様変更の承認前に方式を確定しません。
- **ID上書きの注意点**: 現行コードの `id: doc.id, ...raw` では保存データに `id` があるとドキュメントIDが上書きされるため、レスポンスとカーソルへの影響を確認する必要があります。（※ `transformDoc` 内で `...raw, id: doc.id` に修正し固定済み）

- **書き込み経路の改修**: 上記の作成・更新の全経路において、新ソートフィールドを計算・保存する改修が必要です。
- **旧データ補完（Backfill）の競合リスク**: アプリ側を改修した後に既存データへ新フィールドを一括付与する移行バッチを実行する際、アプリ側で更新された直後のデータを、古い計算値を持ったバッチが上書きしてしまう「先祖返りの競合」が発生し得ます。単なる `WriteBatch` では防げません。

### 予約一覧の50件上限解消・待機予約共存・インデックス安全設計（Copilot最新指摘 #16 対応完了）

Copilotからの最新指摘に基づき、予約一覧の50件上限による待機予約の押し出しリスク解消、失敗ジョブ維持、`postedAt` 基準の決定論的ソート、および複合インデックス安全設計を完了しました：

1. **待機予約・失敗ジョブ・投稿履歴の分離取得による非欠落保証**:
   - `src/hybrid_saas_routes.js`（`GET /api/autopilot/jobs`）: 単一の `limit(50)` による全ステータス一括取得を撤廃。
   - ステータス指定なし（ダッシュボード全体のデフォルト取得）時、以下の3系統を並行取得（`Promise.all`）してマージ：
     - `pending`（待機中予約スロット）: 最大200件まで優先取得。過去ログがどれだけ増えても待機枠が押し出されない構造を保証。
     - `failed`（配信エラー）: 最大50件取得。ユーザーがエラー原因を確認・削除できるよう確実に保持。
     - `posted`（投稿完了履歴）: 要求上限（デフォルト50件、最大200件）を取得。
2. **クエリパラメータの検証・上限設定（`status` / `limit`）**:
   - `limit`: 数値・正の整数検証を実施（不正値・負数・NaNはデフォルト50件にフォールバック）。安全上限を `Math.min(parsed, 200)` で200件に固定。
   - `status`: `pending` / `posted` / `failed` の個別指定取得に対応。
3. **投稿履歴の `postedAt` 降順整列と決定論的フォールバック仕様**:
   - `posted` ジョブ: `postedAt` の降順（最新順）で整列。
     - 日時欠損時のフォールバック階層: `postedAt` -> `scheduledAt` -> `updatedAt` -> `createdAt` -> `0` (Epoch 0 として末尾に安全配置)。
     - 同日時タイブレーク: `String(b.id || '').localeCompare(String(a.id || ''))`（ID降順）により、ソート順の揺らぎを完全排除。
   - `pending` ジョブ: `scheduledAt` の昇順（直近予約が先頭）。フォールバック: `scheduledAt` -> `createdAt` -> `updatedAt` -> `0`。タイブレーク: ID昇順。
   - `failed` ジョブ: `failedAt` / `updatedAt` / `scheduledAt` の降順。タイブレーク: ID降順。
4. **必要なFirestore複合インデックスの策定と本番Fail-Safe二重防御**:
   - `firestore.indexes.json` を新設し `firebase.json` へ登録：
     - `(userId ASC, status ASC, postedAt DESC)`
     - `(userId ASC, status ASC, scheduledAt ASC)`
     - `(userId ASC, status ASC, updatedAt DESC)`
   - **本番インデックス非依存のFail-Safe防衛**: 「エミュレーター合格だけで本番インデックスを保証しない」原則に基づき、クエリ側で `orderBy` 付きクエリを `try...catch` で保護。本番Firestoreでインデックスが未作成またはビルド中の場合でも、単一フィールド等価クエリ（`where`）＋インメモリソートへ自動フォールバックし、500エラー（`FAILED_PRECONDITION`）による画面クラッシュを物理的に遮断。
5. **隔離テスト検証（80件規模共存・ソート・バリデーション）**:
   - `tests/autopilot_jobs_separation.test.js`:
     - 過去ログ60件が存在する環境下で、15件の待機予約および3件の失敗ジョブが一切欠落せず共存できることを実証。
     - 全日時欠損ジョブが末尾に正しく整列すること、および同一日時のIDタイブレークを検証。
     - `limit` の不正値補正（50件）および超過制限（200件クリップ）を検証。
